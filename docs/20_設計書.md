# TripDiary 設計書

Nov 14, 2026 · @masatsumaple-creator

要件は [00_要件定義書.md](00_要件定義書.md) を参照してください。本書はプロジェクト構成と技術方針を定めます。数値は仮です。

## 1. 全体方針

| 項目 | 方針 |
|---|---|
| リポジトリ | モノレポ(`frontend/`、`backend/`、`infra/`、`docs/`、`e2e/`) |
| Node.js | 24 LTS |
| 言語 | フロント・バックとも TypeScript(strict) |
| ローカル開発 | docker-compose で MySQL 8 を起動 |
| 静的解析 | バックエンドは oxlint + Prettier(NestJS 12 の標準)。フロントは ESLint(`@nuxt/eslint`)+ Prettier |

### ディレクトリ構成(予定)
```
TripDiary/
├─ backend/    NestJS
├─ frontend/   Nuxt
├─ infra/      Terraform
├─ e2e/        Playwright
├─ docs/
├─ docker-compose.yml
└─ .github/workflows/
```

## 2. システム構成

| 要素 | 構成 |
|---|---|
| 配信 | CloudFront。静的ファイルは S3、`/api/*` は ALB(内部)経由で ECS Fargate へ転送 |
| API | ECS Fargate 上の NestJS |
| DB | RDS(MySQL) |
| 画像 | S3。署名付き URL でブラウザから直接アップロード |
| 地図 | Amazon Location Service |
| 秘密情報 | Secrets Manager |
| 課金対策 | NAT Gateway・インターフェイス型 VPC エンドポイントを置かない。使わないときは `terraform destroy` |

フロントと API は同一オリジンとし、CORS 設定は行いません。開発時は Nuxt のプロキシで `/api` を転送します。

## 3. バックエンド(NestJS)

| 項目 | 方針 |
|---|---|
| フレームワーク | NestJS 12(ESM、TypeScript 6)。相対 import は `.js` 拡張子つきで書く |
| ORM | Prisma 7(`@prisma/adapter-mariadb` を使用)。スキーマとマイグレーションは Prisma Migrate で管理。Prisma Client は `src/generated/prisma` に生成(コミットしない) |
| マイグレーション | 開発時は `npx prisma migrate dev --name <内容>`、本番は `prisma migrate deploy`。`migrate dev` は shadow DB(`prisma_migrate_shadow_db_*`)を作るため、開発用 DB のユーザーにその権限が必要。`docker compose` で DB を初めて作るときは `docker/mysql/init/01-grant-prisma-shadow-db.sh` が自動で付与する。すでに作成済みの DB には、下記の手順で一度だけ付与する |
| 接続設定 | `DATABASE_URL`(`mysql://` 形式)。`PrismaService` が分解してアダプターに渡す |
| API パス | 全エンドポイントを `/api` 配下に置く(ヘルスチェックは `GET /api/health`) |
| 構成 | 機能別モジュール(auth, users, spots, photos, likes, comments, follows, tags, lists, maps)。各モジュールは Controller / Service / DTO に分ける |
| バリデーション | class-validator + ValidationPipe |
| エラー応答 | `{ code, message, fieldErrors? }` に統一(ExceptionFilter で一元化) |
| 認証 | JWT(アクセストークン)+ リフレッシュトークン(HttpOnly Cookie、DB にはハッシュのみ、ローテーション) |
| 認証の詳細 | パスワードは scrypt(Node 標準)でソルト付きハッシュ化。アクセストークンは JWT で有効期限 15 分(`JWT_SECRET` で署名)、`Authorization: Bearer` で送る。リフレッシュトークンは有効期限 14 日の乱数で、HttpOnly・SameSite=Strict・Path=`/api/auth` の Cookie に載せる(本番は Secure も付与)。使うたびに失効させて作り直し、失効済みを再利用された場合はそのユーザーの全トークンを失効させる |
| 認証 API | `POST /api/auth/register`(201)、`/login`(200)、`/refresh`(200)、`/logout`(204)、`GET /api/auth/me`(要アクセストークン)。メールは小文字に正規化。ログイン失敗は、パスワード違いと未登録メールで同じ応答にする |
| 権限 | Guard で認証を、Service で公開範囲・本人確認を検証 |
| スポット API | `POST /api/spots`(201、要ログイン)、`GET /api/spots/:id`(ログイン任意)、`PUT /api/spots/:id`(全項目を置き換え、本人のみ)、`DELETE /api/spots/:id`(204、本人のみ)。投稿者は常にログイン中のユーザーで、リクエストでは指定できない |
| スポット一覧 API | `GET /api/spots?area=<都道府県名>&cursor=<ID>&limit=<件数>`(ログイン任意)。新着順(新しい順)。応答は `{ items, nextCursor }`。`limit` は 1〜50 で省略時 20。`nextCursor` が null なら最後のページ、あれば次のリクエストの `cursor` に渡す。`area` はマスタにない名前なら 400。要約(ID、場所名、エリア、公開範囲、投稿者、本人かどうか、作成日時)だけを返し、感想・住所・緯度経度は詳細で取得する |
| 一覧に含める投稿 | 詳細と同じ公開範囲の規則。未ログインは public のみ。ログイン済みは public、自分の投稿(非公開を含む)、フォローしている相手の followers を含める。この条件は `spots/spot-visibility.ts` の `viewableSpotsWhere` に 1 か所にまとめ、一覧とプロフィールの投稿数で共用する(規則がずれないように) |
| 一覧の絞り込み(追加) | `author=<ユーザー ID>`: そのユーザーの、閲覧できる投稿(プロフィールの投稿一覧)。存在しない ID は空で返す。`following=true`: ログイン中のユーザーがフォローしている人の、閲覧できる投稿(フォロー中一覧)。自分の投稿は含まない。未ログインは 401。`area`・`cursor`・`limit` と組み合わせられる |
| フォロー API | `POST /api/users/:id/follow`(フォロー)、`DELETE /api/users/:id/follow`(解除)。どちらも要ログインで、200 と `{ isFollowing, followerCount }` を返す。何度実行しても同じ結果(同時に実行しても重複せず、エラーにしない)。自分自身は 400(`CANNOT_FOLLOW_SELF`)、存在しない・不正な ID は 404 |
| プロフィール API | `GET /api/users/:id`(ログイン任意)。`{ id, name, followerCount, followingCount, spotCount, isMe, isFollowing }`。`spotCount` は閲覧者が見られる投稿だけを数える。メールアドレスなどの個人情報は含めない |
| いいね API | `POST /api/spots/:id/like`(いいね)、`DELETE /api/spots/:id/like`(取り消し)。要ログインで、200 と `{ liked, likeCount }`。何度実行しても同じ結果(同時に実行しても重複しない。1 ユーザー 1 投稿につき 1 回)。**自分の投稿には 400**(`CANNOT_LIKE_OWN_SPOT`)。閲覧できない投稿・存在しない投稿は 404 |
| コメント API | `GET /api/spots/:id/comments`(ログイン任意)、`POST /api/spots/:id/comments`(要ログイン、201)、`DELETE /api/spots/:id/comments/:commentId`(要ログイン、204)。一覧は**古い順**(会話として上から読めるように)で、`cursor`(前のページの最後の ID)・`limit`(1〜50、既定 20)でページ送りし、応答は `{ items, nextCursor }`。本文は前後の空白を除き 1〜500 文字。**投稿者も自分の投稿にコメントできる**(質問への返信)。コメントした人は常にログイン中のユーザー |
| コメントの削除権限 | コメントした本人と、その投稿の投稿者だけ(それ以外は 403)。応答の `canDelete` は、閲覧者が削除できるか。別の投稿のコメント ID を指定した場合や、存在しないコメントは 404 |
| 反応の公開範囲 | いいね・コメントは、閲覧できる投稿だけが対象(詳細と同じ規則。閲覧できない投稿は 404 で存在を知らせない)。フォロワー限定の投稿は、フォローするとコメント・いいねできる |
| マイリスト API | `PUT /api/spots/:id/list`(入れる・状態を変える。本文 `{ status }`。status は `visited`(訪問済み)か `wishlist`(行きたい))、`DELETE /api/spots/:id/list`(外す)、`GET /api/me/list?status=&cursor=&limit=`(自分のマイリスト)。どれも要ログインで、リストは本人だけのもの。入れる・外すは 200 と `{ status }`(外したら null)で、何度実行しても同じ結果(同時に実行しても 1 行)。一覧は、状態ごとに、**リストに入れた新しい順**で、`{ items, nextCursor, counts }`(`counts` は、状態ごとの件数でタブの表示用)。`status` を省略すると `visited` |
| マイリストの規則 | **自分の投稿は、作成時に自動で「訪問済み」の行を入れる**(投稿と同じ操作で作る。既存の投稿は、マイグレーションで補った)。自分の投稿の状態は、変更も、外すこともできない(400、`OWN_SPOT_IN_LIST`)。他人の投稿は、「行きたい」でも「訪問済み」でも入れられ、いつでも変更・削除できる。**閲覧できる投稿だけ**が対象で、閲覧できない投稿は 404(存在を知らせない)。入れたあとに閲覧できなくなった投稿(投稿者が非公開に変えた、フォローを解除したなど)は、リストの行は残るが、**一覧にも件数にも出ない**(権限の流出を防ぐ)。権限が戻れば、また見える |
| 詳細のリストの状態 | 投稿の詳細に `listStatus`(`visited` / `wishlist` / `null`)を含める。自分の投稿は、常に `visited` |
| データの持ち方 | `user_spots`(ユーザー × 投稿で一意。状態、登録日時、更新日時)。リストの並び順と、ページングのカーソルには、行の ID(登録順に増える)を使う |
| デッドロックの再試行 | MySQL は、デッドロックが起きると、片方のトランザクションを取り消す(Prisma では `TransactionWriteConflict`、コード P2034)。取り消されたものは、何も書き込んでいないため、再実行しても安全で、MySQL も「再実行する前提で作る」としている。書き込みのサービス(投稿、コメント、フォロー、いいね、マイリスト)は、`retryOnWriteConflict`(`prisma/retry.ts`)で、**少ない回数(3 回まで)だけ再実行する**。他のエラー(入力エラー、一意制約の違反など)は、再実行せず、そのまま返す。並行して書き込みが多いときに、500 にならないためで、実際に、再試行がないと並列のテストで再現した(6 回中 4 回)。書き込みの処理を追加するときは、同じ関数で包む |
| 件数の表示 | 投稿の詳細と一覧の項目に `likeCount`・`commentCount` を含める。詳細には、閲覧者がいいね済みかを示す `liked` も含める(未ログインは false) |
| 本文の表示 | コメントや投稿の本文は、API は入力どおりに返す。HTML として解釈しない(エスケープ)のは、表示側(フロント)の責務で、E2E(`security.spec.ts`)で確認する |
| フォローの仕様 | 承認は不要で、ログイン済みのユーザーなら誰でもフォローできる。フォロワー限定の投稿は、フォローすると見られ、解除すると見られなくなる。フォロー関係は一方向 |
| ページングの方式 | ID の降順(ID は投稿順に増える)をカーソルにするキーセット方式。新しい投稿が増えてもページの重複・抜けが出ない。投稿数が増えて遅くなったら、絞り込み条件に合わせてインデックスを見直す |
| スポットの入力 | 場所名 1〜100 文字(必須)、感想 5000 文字まで、住所 255 文字まで、緯度 -90〜90・経度 -180〜180(どちらかを入れたら両方必須)、エリアタグ 1〜3 個(都道府県名、重複不可、マスタにない名前は不可)、公開範囲(public / followers / private)。`area_tags` の 47 都道府県は、マイグレーションで投入する(id は JIS コード) |
| 公開範囲の判定 | 本人は常に見られる。public は誰でも、followers は投稿者をフォローしているログイン済みユーザー、private は本人のみ。閲覧できない投稿は、存在しない投稿と同じ 404 を返し、存在を知らせない(403 にしない)。閲覧はできるが本人でない人が更新・削除しようとした場合だけ 403。フォロー関係は一方向(`follows` テーブル) |
| ログイン任意の API | `OptionalJwtAuthGuard`。トークンがなければ未ログインとして扱い、トークンが不正・期限切れなら 401 を返す(クライアントがリフレッシュして再試行できるように。未ログイン扱いにすると、期限切れが権限不足に見えてしまう) |
| ID パラメータ | パスの `:id` が整数でない、または DB の INT の範囲外なら、404 を返す(500 にしない) |
| API 仕様 | @nestjs/swagger で OpenAPI(3.0)を**コードから生成**し、`docs/api/openapi.json` をコミットする。仕様書(`docs/` の文書)と食い違う場合は、`docs/` の文書を正とする |
| API 仕様の公開 | 起動したアプリが、Swagger UI を `/api/docs`、仕様書の JSON を `/api/docs-json` で公開する。ログイン不要 |
| API 仕様の書き方 | 応答の型は `class` にして `@ApiProperty` を付け、入力の DTO にも `@ApiProperty` で制約(長さ・範囲・必須)を書く。制約の値は、検証に使う定数(`COMMENT_MAX_LENGTH` など)を共用する。各 API には、タグ、概要、説明、成功時とエラー時の応答を付ける(エラーは `ApiErrors(...)`、認証は `ApiBearerAuth` / ログイン任意は `ApiOptionalBearerAuth`)。**API を変更したら、`npm run openapi` で仕様書を更新して、一緒にコミットする** |
| API 仕様の生成と確認 | `npm run openapi`(ビルドして `docs/api/openapi.json` を更新)、`npm run openapi:check`(生成結果が、コミット済みの仕様書と一致するか確認)。DB には接続せず、ダミーの設定で動くため、環境の値は仕様書に混ざらない。同じコードからは、いつも同じ結果になる(決定的)。`.gitattributes` で、仕様書の改行を LF に固定している |
| テスト | Vitest + Supertest(NestJS 12 の標準)。DB を使うテストは当面 docker compose の MySQL を使う(Testcontainers は CI 整備時に再検討) |
| 写真(アップロード) | 画像は、このサーバーを通さず、**ブラウザが署名付き URL で S3 へ直接 PUT** する。流れは 3 段階: ① `POST /api/spots/:spotId/photos`(形式・大きさを申告 → 署名付き URL を発行。DB に `pending` の行) ② 発行された URL へ、ブラウザが画像を PUT ③ `POST .../photos/:photoId/complete`(画像が実際に置かれたことを、**S3 の実際の大きさ・形式で**確かめて `ready` にする。違えば、行も画像も消して 400)。表示は `ready` だけ。本人の投稿だけに付けられる・外せる(閲覧できない投稿は 404、閲覧できるが本人でなければ 403) |
| 写真の決まり | 1 枚 5MB 以下、1 投稿 20 枚まで、JPEG・PNG・WebP。アップロード用の URL は 5 分、署名に種類と大きさを含める(S3 が、別の値の PUT を拒否する)。20 枚の上限は、発行の後にも数えて、同時の発行でも超えないようにする。1 時間を過ぎても完了しない `pending` は、上限に数えず、次の発行のときに画像ごと片付ける |
| 写真(表示) | 投稿の詳細は `photos: [{id, url}]`、一覧・マイリストのカードは `coverPhotoUrl`(先頭の 1 枚)。URL は、**S3 の署名付き URL(1 時間)**で、**公開範囲は、URL を発行した時点で確かめる**(閲覧できない投稿は、そもそも投稿ごと返さない)。期限が切れたら、投稿を取り直す。URL を作れないとき(保存先の障害など)は、写真だけを出さず、投稿は返す。写真・投稿を消すと、画像も消す(S3 の削除に失敗しても、利用者からは見えない。ログに残す) |
| 写真の保存先 | 環境変数 `S3_BUCKET`(必須)・`S3_REGION`・`S3_ENDPOINT`(ローカルの S3 互換サーバー用)。認証は、AWS の標準(ECS はタスクロール)。ローカル・CI は、docker compose の `s3`(S3Mock、`localhost:9090`。署名の検証はしない)を使う。**S3 による署名の検証(別の種類・大きさの PUT の拒否)は、AWS 上で確認する** |
| 静的解析 | oxlint(NestJS 12 の標準)+ Prettier |

### 作成済みの開発用 DB に shadow DB の権限を付与する(一度だけ)
`docker compose` で DB を作った後に初期化スクリプトを追加した場合や、`migrate dev` が「shadow database を作成できない(P3014)」で失敗する場合に実行する。

```bash
docker exec tripdiary-db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "GRANT ALL ON \`prisma\\_migrate\\_shadow\\_db%\`.* TO \"$MYSQL_USER\"@\"%\";"'
```

付与するのは `prisma_migrate_shadow_db` で始まるデータベースへの権限だけで、他のデータベースには影響しない。

## 4. フロントエンド(Nuxt)

| 項目 | 方針 |
|---|---|
| 描画方式 | SPA(`ssr: false`)の静的出力(`nuxt generate`)。Nuxt 4 |
| 開発サーバー | ポート 5173 に固定(バックエンドは 3000)。`/api` は Nuxt の devProxy でバックエンドへ転送し、本番と同じ同一オリジン構成にする |
| 状態管理 | Pinia |
| スポット API の呼び出し | `useSpotsApi()`(`composables/`)が、認証ストアの `authFetch` 経由で呼ぶ。ログインしていればトークンを付け、期限切れ(401)なら自動でリフレッシュして再試行する。未ログインでも公開投稿の一覧・詳細は取得できる。API の 404 は「存在しない」と「閲覧できない」を区別しないため、画面も同じ文言で表示する |
| 一覧の取得 | エリアの絞り込みを素早く切り替えたとき、遅れて届いた古い応答で上書きしないよう、リクエストの世代を管理する。「もっと見る」は `nextCursor` を次のリクエストに渡す |
| 「近くのスポット」の取得 | 一覧 API をエリアごとに呼び(`limit=6`)、投稿自身を除いて新着順に 5 件へまとめる。専用の API は設けない |
| モック画面 | まだ実 API につないでいない画面(S-08 地図のみ。API が未実装)は、ダミーデータで表示し、「モックです」と明示する。ダミーの詳細は `/mock/spots/:id` に置き、本実装の ID と衝突させない。実画面に置き換えたモック(S-07、S-03、S-06 など)は、その PR で削除した(見た目は画面設計書と git の履歴に残る)。デプロイの前までに、残りもすべて置き換える |
| 認証の扱い | アクセストークンはメモリ(Pinia)にだけ保持し、localStorage には保存しない。起動時にリフレッシュ API でセッションを復元する。401 のときはリフレッシュして 1 回だけ再試行し、同時に複数の 401 が起きてもリフレッシュは 1 回にまとめる。ログインが必要な画面はルートミドルウェア(`auth`)で保護し、未ログインならログイン画面へ移動して、ログイン後に元の画面へ戻す(戻り先はサイト内のパスのみ許可) |
| スタイル | Tailwind CSS |
| 地図 | MapLibre GL JS + Amazon Location Service |
| 画像 | アップロード前にブラウザ側で縮小(長辺 1600px 程度) |
| テスト | Vitest(happy-dom、globals 方式)+ Vue Test Utils(単体)、Playwright(E2E、`e2e/`)。テストファイルは `app/` 配下に `*.spec.ts` で置く |

## 5. CI/CD

| 項目 | 方針 |
|---|---|
| CI | GitHub Actions(`.github/workflows/ci.yml`)。PR と main への push で、バックエンドとフロントエンドを別ジョブで並行実行する。同じブランチの古い実行は取り消す |
| CI(バックエンド) | MySQL 8.4 をサービスとして起動し、`prisma generate` → lint → `nest build` → **API 仕様書の差分チェック**(`node dist/openapi/generate-openapi.js --check`。コードから生成した内容と、`docs/api/openapi.json` が一致しなければ失敗する)→ 単体テスト → `prisma migrate deploy`(空の DB に全マイグレーションを適用できることの確認を兼ねる)→ e2e の順に実行する。`DATABASE_URL` と `JWT_SECRET` は CI 専用のテスト用の値をワークフローに直接書く |
| CI(フロントエンド) | `nuxt prepare` → lint → 型チェック → 単体テスト → `nuxt generate`(デプロイと同じ静的出力が作れることの確認) |
| ブランチ保護(main) | GitHub のリポジトリ設定。`Backend (lint, build, unit, e2e)`、`Frontend (lint, typecheck, unit, generate)`、`E2E (Playwright)` の 3 つのチェックが通らないと、PR をマージできない。最新の main への追従(strict)は求めない。force push と削除は禁止。承認レビューは必須にしない(個人開発のため)。管理者は例外にできる(緊急時の逃げ道)。ジョブ名を変えるとチェックが見つからずマージできなくなるため、`ci.yml` のジョブ名を変えるときはこの設定も更新する |
| CI(E2E) | `E2E (Playwright)` ジョブ。MySQL(`tripdiary_e2e`)を起動し、バックエンド・フロントの依存を入れ、Chromium を入れて `e2e/` の `npm test` を実行する。失敗時はレポートとトレースをアーティファクトとして 7 日間保存する。CI では 1 回だけ再試行する。このジョブも、ブランチ保護の必須チェックに含める |

### テストの方針
| 層 | ツール | 対象と方針 |
|---|---|---|
| 単体 | Vitest(バックエンド・フロント) | 純粋な処理(パスワードのハッシュ化、入力の整形、ページングの計算など)と、ストア・API クライアント |
| API 結合 | Vitest + Supertest(`backend/test/`) | 機能ごとに 1 ファイル。実際の MySQL を使い、権限・公開範囲・入力検証・エラー応答を網羅する。テストごとに別のユーザーを作る |
| API 仕様 | Vitest(`backend/test/openapi.e2e-spec.ts`)+ CI の差分チェック | 仕様書が正しい OpenAPI か(`swagger-parser` で検証)、実際の API をすべて説明しているか(漏れ)、認証の記述(必須・ログイン任意・なし)、エラー応答が共通の形か、入力の制約が実際の検証と同じ値か、内部の項目(パスワードのハッシュなど)や、他人に見えるスキーマへのメールアドレスが含まれないか、Swagger UI が公開されているか。コミット済みの仕様書との一致は、CI で確認する |
| E2E | Playwright(`e2e/`) | 実際にバックエンドとフロントを起動し、ブラウザで主要な流れを確認する。API の確認は結合テストに任せ、画面を通した流れ(登録、投稿、閲覧、権限による見え方)に絞る |

- 機能を追加する PR には、その機能のテストを含める(後からまとめて足さない)。
- バックエンドの結合テスト(`backend/test/`)は、ファイルごとに並列に、同じ DB で動く。テストが作ったユーザーの後始末(`afterAll`)は、ファイルごとに異なるメールの接頭辞(`e2e-auth-`、`e2e-spots-`、`e2e-follows-`、`e2e-reactions-`、`e2e-lists-`)と実行ごとの印の両方で絞り、範囲を狭くして削除し、`retryOnWriteConflict` で包む。全ユーザーを走査する条件にすると、他のファイルの書き込みとロックが競合し、デッドロック(`TransactionWriteConflict`)で 500 になる。新しいテストファイルは、固有の接頭辞を使う。
- 結果を厳密に確認するテストは、他のテストが使わないエリアを専用に使う。呼び出しごとに別のユーザーを作る(ラベルが同じでもメールが重複しないように、連番を付ける)。
- 判定ロジック(公開範囲など)を壊すとテストが失敗することを、PR の作成時に確認する(破壊テスト)。確認は、E2E の URL 判定の甘さを見つけるなど、実際に効果があった。
- E2E の URL の確認は、パス名で厳密に判定し、再試行つきの待ち方(`expect(page).toHaveURL(...)`)で確認する。`/login?redirect=/spots/new` のように別の画面の URL に同じ文字列が含まれることがあり、また、ログイン直後はヘッダーのユーザー名が、ページ移動の完了より先に表示されるため。

### E2E の種類(`e2e/tests/`)
| ファイル | プロジェクト | 内容 |
|---|---|---|
| `auth.spec.ts`、`spots.spec.ts`、`profile.spec.ts`、`reactions.spec.ts` | functional(PC 幅) | 認証と、スポットの投稿・閲覧・権限、プロフィールとフォロー(フォローで見られる投稿が変わる、未ログインのフォローはログインへ移動して戻る、自分のプロフィール、ページング、存在しないユーザー)、いいね(件数・取り消し・自分の投稿はボタンなし・未ログインはログインへ)、コメント(投稿・古い順・削除権限・ページング・HTML が実行されない)、フォロー中の一覧、マイリスト(`mylist.spec.ts`: 詳細のボタン、タブと件数、入れた新しい順、自分の投稿は操作なし、状態の変更・削除、ページング、非公開にされた投稿は見えない、本人だけ) |
| `paging.spec.ts` | paging | 専用エリアで件数を厳密に確認する(1 つずつ実行) |
| `security.spec.ts` | functional | 未ログインの 401、他人の投稿の変更が 403/404、存在を知らせない応答、一覧に他人の非公開が出ない、アカウントの有無を知らせない応答、想定外の項目の拒否、リフレッシュトークンが HttpOnly・SameSite=Strict・Path=/api/auth の Cookie にだけ入ること、保存領域と URL にトークンが残らないこと、ログアウトで Cookie が無効になること、投稿内容の HTML・スクリプトが実行されないこと(一覧・詳細・編集フォーム)、ログイン後の戻り先が外部サイトにならないこと |
| `a11y.spec.ts` | functional | axe-core で WCAG 2.0/2.1 の A・AA を検査する。ログイン、新規登録、一覧、詳細、投稿・編集フォーム、「見つかりません」の画面。違反があれば、ルールと要素を表示して失敗する |
| `responsive.spec.ts` | mobile(Pixel 7 相当) | 下部のタブバー(ログイン状態で項目が変わる)、横にはみ出さないこと、1 列のカード、固定のタブバーに最後の項目や保存ボタンが隠れないこと、スマートフォン幅でのアクセシビリティ |

### アクセシビリティの方針
- 画面を追加・変更するときは、`a11y.spec.ts` の検査対象に加える。
- 文字と背景の色は、コントラスト比 4.5 以上にする(白文字のボタンは `bg-sky-700` 以上の濃さ)。
- すべての入力欄に、ラベル(または `aria-label`)を付ける。地図のように、中に操作できる要素を含むものに `role="img"` を付けない(`role="group"` にする)。
- 各画面に題名を付ける(`useHead({ title })`)。題名は「<題名> | TripDiary」の形になる(`app.vue`)。`<html>` には `lang="ja"` を付ける(`nuxt.config.ts`)。

### E2E の構成(`e2e/`)
| 項目 | 内容 |
|---|---|
| 分離 | 開発用とは別の DB(同じ MySQL コンテナの `tripdiary_e2e`)とポート(バックエンド 3100、フロント 5174)を使う。開発中のデータに触れず、開発サーバーを起動したままでも実行できる |
| 起動 | Playwright の `webServer` が、バックエンド(`npm run start`)とフロント(`npm run dev -- --port 5174`)を起動する。起動済みなら再利用する(ローカルのみ) |
| 準備(global-setup) | E2E 用 DB に `prisma migrate deploy` を適用 → 前回の残りのユーザーを削除 → 開発サーバーの初回アクセスで起きる再読み込みを避けるため、先に各ページを一度開く |
| データ | テストごとに API で一意のユーザー(メールの接頭辞 `e2e_`)を作る。並列に実行しても混ざらない。名前も一意にし、結果は自分のデータだけで判定する |
| 専用エリア | 件数を厳密に確認するテスト(一覧のページング、空の表示)は、他のテストが使わないエリアを専用に使う。ページングは `paging` プロジェクトとして別に実行し、投稿は終了時に削除する |
| 後始末(global-teardown) | 接頭辞 `e2e_` のユーザーを DB から削除する(投稿・タグ・フォロー・トークンは外部キーの CASCADE で連動して消える)。`E2E_KEEP_DATA=1` で残せる |
| ログイン済みにする | ログイン API を、ページと同じ Cookie 領域へ送る(`page.request`)。次にページを開くと、リフレッシュトークンでセッションが復元される。毎回ログイン画面を操作しない |
| 開発サーバーの設定 | `frontend/nuxt.config.ts` は、環境変数 `API_PROXY_TARGET`(/api の転送先)と `NUXT_DEVTOOLS=false`(DevTools の無効化)で E2E 用に切り替える。未指定なら従来どおり |

### E2E 用のデータベースを作成する(作成済みの開発用 DB 向け、一度だけ)
`docker compose` で DB を作った後に初期化スクリプト(`docker/mysql/init/02-create-e2e-database.sh`)を追加した場合は、次のコマンドで作成する。新しく作る DB では自動で作成される。

```bash
docker exec tripdiary-db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "CREATE DATABASE IF NOT EXISTS tripdiary_e2e CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; GRANT ALL ON tripdiary_e2e.* TO \"$MYSQL_USER\"@\"%\";"'
```

実行は `e2e/` で `npm install`、`npx playwright install chromium`(初回のみ)、`npm test`。
| デプロイ | `workflow_dispatch` の手動実行。GitHub OIDC で AWS へ認証 |
| バックエンド | Docker build → ECR push(タグは git SHA)→ ECS サービス更新 |
| フロントエンド | `nuxt generate` → S3 sync → CloudFront invalidate |
